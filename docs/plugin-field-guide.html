Plugin Field Guide

A plugin is code you upload once, then install as one or more instances into fixed spots across the storefront. Each instance talks back to Belanjaku through exactly two guarded doors. Seven pictures below cover the whole mechanism.

1 · Big picture 2 · Plugin vs. instance 3 · manifest.json 4 · Your workflow 5 · Where it renders 6 · Adding a UI 7 · Data & GraphQL
01

The big picture

Four parties, one narrow data pipe. You build code and hand it off; someone else decides where it's installed; the storefront does the rendering.

02

One plugin, many instances

You write and version the code once. It gets installed as many independent instances — different sellers, different slots, different scopes — each configured on its own.

Override rule: a product-scoped instance always wins over an all_product_pages one for that exact SKU — Instance C above would be skipped on any product page where a more specific instance also exists.
03

manifest.json, at a glance

Every upload needs exactly one of these. It's not read by your code at runtime — it's read once, by the upload service, to validate and describe what you're shipping.

runtime_key · name · version · entry Identity — runtime_key must match the string you pass to createPlugin()
props_schema Config a seller can set per install — becomes the props your setup() reads
data_schema Shape of the data your plugin is allowed to submit — validated server-side
rules_schema Which slots it may go into, and who can add / edit / delete submitted data
Full field-by-field reference: docs/manifest.md
04

Your workflow, locally

Six steps, start to finish. The only unusual one is #4 — there's no live-reload storefront to test against, so you fake the host yourself in a blank page.

05

Where it renders, and what it can do

Not "anywhere." A plugin only ever gets an empty box in one of a handful of fixed spots — never a new spot of its own.

Can
Render into its slot full control of that one box — plain DOM, React, whatever you like
Read public data anything approved & submitted before, for the scope it asks for
Submit new data reviews, ratings, anything — tied to a product, store, or the whole tenant
Call two GraphQL doors a guarded read and a guarded write — nothing else is reachable
Can't
Create a new slot the five spots are fixed in swift-page's own code
Query arbitrary GraphQL no seller/contributor operations — only the two public, tenant-scoped ones
Run on the server browser-only — there's no server-side render step for plugins
Skip cleanup for free you must return a destroy() or you leak listeners on every re-mount
06

Adding a UI, concretely

The host's whole job is handing you an empty <div>. Everything inside it is yours — the SDK just wires the handoff and the cleanup.

Styling: the host hands you a theme object (text color, button color, radius, font) pulled from the storefront's own theme, so your widget can match the page it's sitting in without hardcoding colors.
07

Data & GraphQL, clarified

One pipe, two directions. Nothing else is reachable — a plugin never talks to Plugin Service directly, and never sees the full GraphQL API.

Scope is the key concept: every record is tagged product, store, or global. Write under one, read back under the exact same one — a review saved as product won't show up if you ask for store.
